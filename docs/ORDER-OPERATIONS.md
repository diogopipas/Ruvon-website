## Durable worker

`POST /api/internal/jobs/run` requires `Authorization: Bearer <RUVON_WORKER_SECRET>`. It claims up to ten due jobs with two consumers, 90-second leases and fencing tokens, draining newly committed work within the same invocation when budget remains. Provider calls share a 20-second invocation deadline. The final monitoring ping has at most two five-second attempts within an overall 23-second deadline, leaving margin for the final database health acknowledgement before the Cron HTTP timeout. Ping retries never repeat job handlers. Health success is recorded after the ping; persistent monitoring failure leaves the last successful run unchanged and logs only a safe error classification. Transactions commit intent before external work; provider calls never run inside database transactions. Claim expiry recovers crashes. An expired worker cannot finish a job or apply financial/delivery facts.

On Supabase enable `pg_cron`, `pg_net` and Vault. Store environment-specific `ruvon_worker_url` (HTTPS URL ending `/api/internal/jobs/run`) and `ruvon_worker_secret` in Vault through a trusted admin connection. Then invoke `public.commerce_install_schedule()` as a privileged internal role. It installs `ruvon-orders-worker` every 30 seconds with a 25-second HTTP timeout. This is now installed on the isolated sandbox, and consecutive scheduled HTTP calls returned 200. Production scheduling has not been installed. Keep the stable sandbox alias when replacing a Preview; verify the new deployment before repointing it. The protected-preview Vault destination also contains private Vercel automation authentication; never print it. Verify actual invocations before allowing new orders. Next.js `after()` only nudges existing durable work after successful starts, merchant commands and inbox persistence; it is not the scheduler.

Retry delays are approximately 5 / 30 / 120 / 300 / 900 seconds with jitter and `Retry-After`. Unknown operations stay unknown; no new provider key is generated by a retry. Pending refunds are not declared failed by a local timer. Five-minute unresolved operation sweeps create review cases. Exhausted jobs create an actionable case.

Migration 014 adds database-time guards and broader work reconstruction. It was applied to the isolated hosted sandbox on 20 October; full schema/ACL parity passed for 25 public tables and 56 application functions, with legacy rows preserved. Rebuilt notifications retain their original event/job identity. Existing failed jobs, active leases and quarantine are never reset by a sweep. Return relationships recorded from verified provider facts reconstruct the same return read; older records can recover that relationship by reading the existing outbound resource. No replacement trip is created. Reconciliation of existing financial operations also continues after fulfilment completes or cancels.

## Availability and launch gates

New checkout requires the exposure flag, matching complete provider configuration, a healthy worker (last successful run within 120 seconds), an enabled/open/unpaused store with heartbeat within 90 seconds, stock and unexpired capability evidence in `commerce_capabilities`. Merchant acceptance uses database time and a three-minute deadline. Preparation requires confirmed capture **and** outbound booking.

Capability rows are maintained only through a trusted database admin connection, with verifier, evidence reference and explicit expiry. Never mark a capability verified merely to unlock the UI. Required common evidence includes marketplace onboarding, the chosen authorisation method, void/refund, split hold/schedule, settlement evidence, Uber booking recovery/returns and notifications. Live additionally requires credential rotation, sandbox acceptance, Portugal alcohol approval, monitoring, legal policies and production pilot approval. Sandbox acceptance is not a prerequisite for starting the protected sandbox test itself.

For an incident set `RUVON_LIVE_CHECKOUT_ENABLED=false` or pause the store, redeploy environment changes, and verify the public interest flow. **Do not set payments mode to disabled while existing orders need recovery.** Leave webhook inbox, Cron, refunds and delivery reads enabled. Never delete unresolved operations or reset a key to make a button work.

## Exceptions

In the merchant dashboard, a pending action blocks other commands for that order. **Repetir a mesma ação** reuses the original command and its contents, even when polling has already advanced the order or removed a return form. Once the server confirms the action, **Atualizar pedido** only reloads its state; it does not submit the command again. A version/validation refusal must also be followed by that read before choosing a new action. Timeouts, rate limits and server failures do not establish refusal. Commands for other orders remain independent.

Retry payloads remain in memory while the dashboard is mounted. Return notes are not stored in local/session storage. After a reload or new sign-in, inspect the current server state before choosing an action; do not treat missing browser confirmation as failure. Database replay/version guards and uniquely keyed background operations remain authoritative. If access is denied, orders, stock and recovery controls disappear and heartbeats stop.

Open `/admin/orders` with a named operational identity. Inspect timeline, provider operations, attempts, jobs and cases before acting. Reconcile retries the same operation, including authoritative reads for already terminal facts. A 409 means refresh the order/version; it is not permission to mint another financial operation.

- Unknown payment/booking: reconcile stored identities; retain uncertainty until authoritative evidence exists. Do not charge, refund as cancelled, or dispatch again based only on missing callbacks.
- Merchant rejection/timeout before fulfilment: automatic cancellation requests void or full refund and releases unused stock only after safe closure.
- Customer request after acceptance, pickup disagreement, refusal/age failure, missing/wrong/damaged goods: hold for review. A named admin can acknowledge and resolve a case with a recorded reason, responsible party and summary. Resume requires all cases resolved, no uncertain financial operation and a compatible verified physical/payment state. Record-only resolution leaves the order held. Evidence storage and complete exception verification are still outstanding; do not edit state directly.
- Return: follow the provider-created return leg. The merchant dashboard accepts a condition note and explicit saleable quantities bounded by consumed quantities, after a verified return. Damaged/unconfirmed stock is never automatically restored. Financial resolution remains a separate approved action.
- Refund: preview amount and component allocation. Successful plus reserved/unknown refunds count against available capture balance. Customer refund does not establish merchant recovery.
- Settlement: a future clearing date is not proof of bank payout. The present job opens a verification case and cannot complete the automated settlement path.

With migration 014, preparation review is due twenty minutes after confirmed booking and a return review after forty-five minutes without confirmed return receipt. An early or obsolete invocation cannot open those cases. The original delivery may legitimately progress from `canceled` to `returned`; the separate return leg still requires its own receipt confirmation, and neither fact is delivery to the customer. Existing dispute holds remain disputed while physical return facts continue.

`NO_COURIER_ASSIGNED` means a fresh authoritative outbound read still reports `pending` at ten minutes. `DELIVERY_OVERDUE` means an active outbound delivery remains unresolved at the approved ETA plus fifteen minutes. Inspect the same trip and its provider status; these cases hold clearing and do not automatically cancel an active trip or refund it as safely closed. Cancellation timing/costs and the automatic compensation contract remain to be implemented and verified with Uber. [Uber's status reference](https://developer.uber.com/docs/deliveries/daas/references/api/webhooks/delivery-status-webhook) distinguishes an unassigned `pending` delivery, assigned `pickup`, and separate outbound/return progression.

The sandbox admin financial recovery update retains one approved command while its response is uncertain. **Repetir a mesma ação** repeats the original UUID, version, amount, allocation and reason; **Atualizar pedido** performs only a read after acknowledgement/refusal. Other commands remain disabled until recovery completes. Persisted unresolved refunds are shown after reload and block new refund buttons; inspect/reconcile that refund's existing operation. Browser attempt payloads remain in mounted memory only. A successful command acknowledgement reserves/queues work and does not establish provider refund success or merchant recovery. Read/write access loss removes private data and stops polling. These UI changes were published to the protected Preview on 20 October. Browser fixtures cover replay/privacy; hosted financial command acceptance remains outstanding.

Configuration indicators validate local settings; provider availability and commercial enablement still require evidence.

The operator account is now confirmed and authorised only in `Ruvon-transaction-sandbox` (`pdabphxqkszajvxilxat`). Sign in at the stable sandbox `/merchant/login`, then open `/admin/orders/health`. Sign in again after a role change so the JWT used by database RPCs carries the current role. Never share the personal password or copy this account into production as a deployment step.

The panel lists at most 100 oldest failures per queue plus 30 recent control audit entries. It includes quarantined callbacks with no order, failed or overdue jobs, expired leases, uncertain provider operations and failed notifications. It never exposes raw payloads, notification recipients, provider requests/keys or customer addresses. Open an order's detail for financial reconciliation using its existing operation.

Enter a short operational reason before pausing/resuming a store or retrying a callback. Store commands use `operations_version`; merchant and automatic pause changes invalidate stale commands. Resume requires an enabled store and a fresh heartbeat, while hours, stock and capability checks still apply. Pausing affects new checkout eligibility; existing recovery jobs continue.

Only failed inbox jobs whose verified event remains pending can be retried globally. The command reuses the job/reference and records the actor/reason once. Quarantine is not automatically made trustworthy by clicking retry; investigate correlation or provider facts first. Financial jobs and active/expired leases have no global reset control; the worker reclaims expired leases and order reconciliation preserves financial keys.

If a response is lost, choose **Repetir a mesma ação** to reuse its UUID. A 409 requires reloading the current state before a new intent. **Fechar tentativa e atualizar** reads the current state; it does not undo an accepted action. Control history is append-only.
