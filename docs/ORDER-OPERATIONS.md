# Order operations

This runbook describes the local implementation and the required setup. Read [implementation status](IMPLEMENTATION-STATUS.md) before enabling anything. Recovery routes and jobs must remain available when new checkout is paused.

## Environment preparation

1. Use separate production and sandbox Supabase projects. Back up the target, verify migration parity, then apply 006–011 in order after existing 001–005. Do not rewrite financial history or copy test orders to production.
2. Configure environment-matched provider credentials, dedicated webhook authentication, Auth publishable key, `RUVON_WORKER_SECRET` and `RUVON_RATE_LIMIT_SECRET`. Secrets are server-only except the Auth publishable key. Keep `RUVON_LIVE_CHECKOUT_ENABLED=false`.
3. Create named Supabase Auth users. Insert `store_users` memberships through a trusted administrative connection. Operational administrators require trusted `app_metadata.role = operations_admin`; user metadata does not authorize finance actions. The existing analytics password does not grant commerce access.
4. Configure real store addresses, exact postcodes, Lisbon weekly hours (`0` Sunday … `6` Saturday; arrays of `{start: HH:MM,end: HH:MM}`), account references and verified clearing settings. Overnight spans are supported. Set explicit SKU compliance, dimensions, weight, stock and prices. Stores default disabled/paused.
5. Finish notification integration, settlement evidence, cancellation/exception policies and the outstanding tests. Provisioning alone does not satisfy a capability.

The supported stock units/pack recipes are explicit in `lib/server/orders/recipes.ts`. A multipack price is the sum of its physical SKU quantities. Do not seed illustrative catalogue prices as approved store prices. No production seed store or invented stock is included.

## Durable worker

`POST /api/internal/jobs/run` requires `Authorization: Bearer <RUVON_WORKER_SECRET>`. It claims up to ten due jobs with two consumers, 90-second leases and fencing tokens, draining newly committed work within the same invocation when budget remains. Provider calls share a 20-second invocation deadline. Transactions commit intent before external work; provider calls never run inside database transactions. Claim expiry recovers crashes. An expired worker cannot finish a job or apply financial/delivery facts.

On Supabase enable `pg_cron`, `pg_net` and Vault. Store environment-specific `ruvon_worker_url` (HTTPS URL ending `/api/internal/jobs/run`) and `ruvon_worker_secret` in Vault through a trusted admin connection. Then invoke `public.commerce_install_schedule()` as a privileged internal role. It installs `ruvon-orders-worker` every 30 seconds with a 25-second HTTP timeout. This has **not** been run remotely. Verify actual invocations before allowing new orders. Next.js `after()` only nudges existing durable work after successful starts, merchant commands and inbox persistence; it is not the scheduler.

Retry delays are approximately 5 / 30 / 120 / 300 / 900 seconds with jitter and `Retry-After`. Unknown operations stay unknown; no new provider key is generated by a retry. Pending refunds are not declared failed by a local timer. Five-minute unresolved operation sweeps create review cases. Exhausted jobs create an actionable case.

## Availability and launch gates

New checkout requires the exposure flag, matching complete provider configuration, a healthy worker (last successful run within 120 seconds), an enabled/open/unpaused store with heartbeat within 90 seconds, stock and unexpired capability evidence in `commerce_capabilities`. Merchant acceptance uses database time and a three-minute deadline. Preparation requires confirmed capture **and** outbound booking.

Capability rows are maintained only through a trusted database admin connection, with verifier, evidence reference and explicit expiry. Never mark a capability verified merely to unlock the UI. Required common evidence includes marketplace onboarding, the chosen authorisation method, void/refund, split hold/schedule, settlement evidence, Uber booking recovery/returns and notifications. Live additionally requires credential rotation, sandbox acceptance, Portugal alcohol approval, monitoring, legal policies and production pilot approval. Sandbox acceptance is not a prerequisite for starting the protected sandbox test itself.

For an incident set `RUVON_LIVE_CHECKOUT_ENABLED=false` or pause the store, redeploy environment changes, and verify the public interest flow. **Do not set payments mode to disabled while existing orders need recovery.** Leave webhook inbox, Cron, refunds and delivery reads enabled. Never delete unresolved operations or reset a key to make a button work.

## Exceptions

Open `/admin/orders` with a named operational identity. Inspect timeline, provider operations, attempts, jobs and cases before acting. Reconcile retries the same operation, including authoritative reads for already terminal facts. A 409 means refresh the order/version; it is not permission to mint another financial operation.

- Unknown payment/booking: reconcile stored identities; retain uncertainty until authoritative evidence exists. Do not charge, refund as cancelled, or dispatch again based only on missing callbacks.
- Merchant rejection/timeout before fulfilment: automatic cancellation requests void or full refund and releases unused stock only after safe closure.
- Customer request after acceptance, pickup disagreement, refusal/age failure, missing/wrong/damaged goods: hold for review. A named admin can acknowledge and resolve a case with a recorded reason, responsible party and summary. Resume requires all cases resolved, no uncertain financial operation and a compatible verified physical/payment state. Record-only resolution leaves the order held. Evidence storage and complete exception verification are still outstanding; do not edit state directly.
- Return: follow the provider-created return leg. The merchant dashboard accepts a condition note and explicit saleable quantities bounded by consumed quantities, after a verified return. Damaged/unconfirmed stock is never automatically restored. Financial resolution remains a separate approved action.
- Refund: preview amount and component allocation. Successful plus reserved/unknown refunds count against available capture balance. Customer refund does not establish merchant recovery.
- Settlement: a future clearing date is not proof of bank payout. The present job opens a verification case and cannot complete the automated settlement path.
